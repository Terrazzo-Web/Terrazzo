# Rust blocking I/O and Tokio worker stalls

Implementation follow-up: findings 1–4 from the numbered summary are now addressed in the editor/Git, Tantivy, and tile-persistence runtime paths. Git output and editor filesystem operations use Tokio; long async traversals yield periodically. Account-name lookups and Tantivy's synchronous APIs run on Tokio's blocking pool, with bounded query concurrency. Tile persistence uses ordered async writes and a normal-shutdown flush; mutations return before their queued disk writes finish. Login, logging, and the other deferred paths remain outside this change. The audit below records the original findings and original source line numbers.

Audit date: 2026-11-07. Static review of the current working tree; no runtime latency measurements or code changes. Repository-wide Rust searches followed by inspection of runtime call paths. Build scripts, procedural macros, standalone tools, browser code, and tests were separated from backend runtime findings. This is a source audit, not a guarantee about every dependency's internals.

**Yes: there are multiple confirmed blocking operations on async execution paths.** No Rust uses of `spawn_blocking` or `block_in_place` were found. `tokio::spawn` does not isolate synchronous work from runtime workers. Severity below reflects potential impact and frequency, not measured duration.

## Short stalls and initialization paths

- **PTY creation and resize:** `pty/src/lib.rs:61` is async but directly allocates the PTY, opens its slave, and spawns the shell. `pty/src/raw_pty.rs:15`, `:53`, `:75` contain synchronous open/pty/fcntl/ioctl operations; `pty/src/command.rs:178` ultimately calls synchronous process `spawn`. Tokio child waiting is async, but process creation itself is synchronous. Resize issues an ioctl directly. Usually short, but no latency bound follows from the async wrapper.
- **PTY streaming is substantially different:** the normal open path sets `O_NONBLOCK` before splitting (`pty/src/lib.rs:83`), and `pty/src/pty.rs` uses `AsyncFd` readiness plus `try_io`. Those read/write calls are intended to return promptly rather than wait for data. The public low-level `Pty::new` API does not itself enable nonblocking mode, so other callers must uphold that requirement before streaming.
- **Client certificates:** `remote/client/src/load_client_certificate.rs:41` is async but synchronously checks/reads certificates and stores generated PEM files (`:161`). These run during client/agent setup rather than every request.
- **Root CA and trusted PEM loading:** `remote/server/src/server/root_ca_configuration.rs:28` synchronously checks/reads/creates/writes CA files and permissions. `remote/common/src/security_configuration/trusted_store/load.rs:31` synchronously reads PEM files. Relevant during setup/reconfiguration; impact depends on when callers invoke them.
- **Native trust roots:** `remote/common/src/x509/native_roots.rs:9` lazily loads OS certificates and parses them under `OnceLock`. The first caller pays synchronous loading/crypto cost; concurrent first callers can wait for initialization. `security_configuration/trusted_store/native.rs` exposes this through trust-store configuration.
- **Other setup/CLI I/O:** PID files, daemonization output files, password prompts/stdin reads, endpoint-file writes in gateway/demo startup, and initial tile/config loads are synchronous. They matter if executed after runtime startup, but are not recurring request-path findings. A password prompt can wait indefinitely for input.

## Other synchronous work that can occupy workers

Synchronous work need not perform I/O to delay Tokio scheduling. Conversion handlers (`terminal/src/converter/service.rs:39`) call JSON/YAML/Base64/JWT/X509 recognizers and serializers directly; PDF loading Base64-encodes the entire file (`text_editor/fsio/service.rs:41`); folder listings sort synchronously; certificate creation/parsing/signature verification and index fingerprint scans also consume the polling thread. Large inputs and large repositories warrant bounds or bounded offloading. Ordinary JWT HMAC work is synchronous too, but is a lower priority than PBKDF2 and large transformations.

There are synchronous mutexes/RwLocks throughout backend state, dynamic configuration, signaling, health, and caches, plus DashMap locking. Acquiring a contended synchronous lock can park a worker. Their presence alone is not a defect: short in-memory critical sections can be reasonable. The strongest cases here are the locks held over disk writes, filesystem discovery, and password hashing. `remote/common/src/security_configuration/common.rs:11` also invokes cache initialization while holding its mutex, so first-use costs serialize callers.

## Recommended order

1. Fix text-file Git subprocess waits, directory metadata/account lookups, PBKDF2 login verification, and tile persistence.
2. Put Tantivy initialization, querying, and writes behind bounded blocking execution or a dedicated index thread. Merely adding `tokio::spawn` will not help.
3. Remove synchronous filesystem checks from editor/config runtime paths; isolate watcher and certificate file operations; make tracing output nonblocking.
4. Measure worker scheduling delay under concurrent terminal streaming, file opens, search/index refresh, login attempts, and tile mutations. Include cold caches and slow filesystem/output sinks. This audit establishes potential stalls, not their durations on a particular machine.

No application changes or tests were run for this report. Existing user modifications were left untouched. Integration helpers and build/tooling contain additional blocking operations but were excluded from production-runtime severity rankings. No production `std::thread::sleep`, explicit blocking channel receive, or nested runtime `block_on` was found by the targeted searches.
