# Replace DynConfig's callback graph with watch channels

## Goal

Allocate one shared `Arc<DynConfig>` at startup. Its watch channels keep their
identity for the lifetime of the process. On file changes, load and merge a
temporary, ordinary `Config`, validate and prepare its changes, then publish
changed values through the existing channels. Never replace the global config or
construct another dynamic config during reload.

“Global” means the single instance shared by backend services, through the existing
startup graph and `Server`. A new static singleton is unnecessary.

## Current behavior

- `config/into_dyn.rs` creates a root `DynamicConfig<DiffArc<Config>>`, derives
  writable server/mesh/ACME views, and attaches a view that saves the config file.
- Reload already constructs a temporary merged `Config`, but selectively copies
  server fields and ACME settings. It does not apply mesh changes.
- `run_server_graph.rs` derives authentication and TLS settings using `view`,
  `view_diff`, and `zip`. Authentication is rebuilt for every server change.
- `run_client_async` uses a mesh view whose returned abort handle controls client
  lifetime. Certificate renewal deliberately republishes the same mesh value to
  restart the client.
- Password changes and ACME credential/certificate changes propagate back through
  writable derived views and implicitly save the file.
- The baseline mesh field is `DynamicMeshConfig`; the temporary `Sender<()>`
  experiment has been undone.

## Proposed data model

Keep three distinct representations:

1. `ConfigFile`: serialized file schema, preserving existing keys and aliases.
2. `Config`: ordinary merged values, used as the throwaway reload candidate.
3. `DynConfig`: stable runtime owner of startup settings and watch senders.

Group values by consumers and consistency requirements rather than creating a
channel for every scalar. Suggested shape (names are illustrative):

```rust
pub struct DynConfig {
    startup: StartupConfig,
    auth: watch::Sender<Arc<AuthState>>,
    terminal: watch::Sender<Arc<TerminalSettings>>,
    filesystem: watch::Sender<Arc<FilesystemSettings>>,
    reload: watch::Sender<ReloadSettings>,
    mesh: watch::Sender<Option<Arc<MeshConfig>>>,
    tls: watch::Sender<Arc<TlsState>>,
}
```

Make senders private; expose current-value and subscription methods. Only the
configuration controller publishes changes. Consumers receive `watch::Receiver`
handles, which are cloneable and provide read-only access.

`AuthState` should hold password verification inputs and token settings/keys
together. `TlsState` should hold ACME settings, renewal threshold, and the prepared
TLS/issuer configuration together. This avoids async derived tasks temporarily
exposing new passwords with old keys, or new ACME settings with an old threshold.
Retain authentication key material when its actual inputs have not changed;
unrelated reloads must not regenerate the random secret used without a password.

## Reload policy

| Group | Fields / behavior |
| --- | --- |
| Authentication | Password, token lifetime, token refresh; publish one coherent state. |
| Terminal | Shell and terminal-cd; apply to newly created terminals. |
| Filesystem/search | Trash, git-trash, Tantivy cache, search refresh/staleness; readers use current settings. Check existing cache lifetimes when changing paths. |
| Reload | Watcher enabled and optional poll strategy; a supervisor starts/stops the corresponding workers dynamically. |
| Mesh | Optional complete mesh config, including WebRTC settings; enable, disable, or restart the client when changed. |
| TLS | Optional ACME config and certificate renewal threshold; rebuild the applicable certificate/issuer state. |
| Startup | Host, ports, tiles file, current-endpoint path, pidfile, private root CA, and server P2P registration remain startup-only initially. Log changed fields as requiring restart. |

The startup-only list follows current consumers: publishing a new value cannot
rebind listeners, reopen tile persistence, or restart P2P registration by itself.
Supporting those changes live requires separate service lifecycle work. Include
certificate renewal threshold in the TLS group explicitly: current selective
server application omits it.

Watch channels are atomic individually, not across the whole config. Consumers
requiring consistency must use a single grouped state. Independent services may
observe a reload at different times; this plan does not promise a transaction
across all channels.

## What can be removed

- `DynConfig.config`, its `Deref` implementation, and the root mutable config graph.
- `dyn_config_file`, the dummy `DynamicConfig<(), RO>` retained for its save side effect.
- `DynamicServerConfig` and `DynamicMeshConfig` wrapper structs after migrating
  their consumers and moving mutation methods to the controller.
- Handwritten clone-on-first-change machinery in `apply_server_config`, and
  `try_set` returning `Err(())` to represent an unchanged config.
- Config-specific `derive`, `view`, `view_diff`, and `zip` callback chains.
- `DiffArc<DynConfig>` in backend/API signatures; use `Arc<DynConfig>`.
- `DiffArc`/`DiffOption` in file and candidate types where they exist only for
  callback change detection; use ordinary `Arc`/`Option` or owned values.

Do not delete `remote/common/src/dynamic_config.rs` in the initial migration:
remote client/server security interfaces, ACME, and tests also use it. Delete its
registry, modes, diff wrappers, and tests only after migrating every remaining
consumer. Search the entire workspace before removing shared exports.

## What needs rewriting

### Construction, application, and persistence

- Split `into_dyn.rs` into construction, reload coordination, and explicit update/
  persistence responsibilities. Preserve `ConfigFile::load`, CLI merge precedence,
  serialization aliases, and defaults in `io.rs` and `merge.rs`.
- Add construction from an initial candidate and an `apply(candidate)` boundary.
  Compare group inputs by value, prepare fallible derived state first, and publish
  only after preparation succeeds. Preserve the active config on preparation error.
- Use `send_if_modified` for changed-only publication and `send_replace` when a
  deliberate publication is required. Publication must retain the latest value
  even when there are no subscribers. Avoid plain `send` for stored config state.
- Give non-`Eq` types explicit semantic comparisons; fresh `Arc` identities are
  not evidence of a configuration change. Reuse ACME's existing value comparison
  where appropriate.
- Serialize reloads and runtime mutation commands through one controller so watcher,
  polling, password updates, and ACME callbacks cannot overwrite newer state.
- Retain a plain accepted/persistable config in that controller, separate from
  the watch storage. Preserve requested startup-only values for persistence while
  keeping the running startup settings unchanged until restart.
- File reloads update runtime state without automatically saving the file again.
  Password and ACME changes explicitly update the persisted representation and
  save it, with save errors reported to the caller/logs. Define save-before-publish
  for commands that must persist before succeeding, especially set-password.
- Record the successfully accepted file fingerprint after loading/preparation,
  rather than marking its timestamp consumed before parsing. Failed loads remain
  retryable. Keep parent-directory watching for atomic file replacement, dedupe
  successful equivalent updates, and suppress write-back loops.

### Runtime readers

- Rewrite `backend/mod.rs`, `server_config.rs`, `root_ca_config.rs`, API routing,
  login, and authentication middleware to use startup fields or watch snapshots.
- Read the mesh client name per `/remotes` request; it is currently captured when
  routes are constructed and would otherwise remain stale after mesh reloads.
- Update text-editor filesystem/search readers, following references from
  `text_editor/fsio/api.rs`, and all remaining `DynamicServerConfig` consumers.
- Clone an `Arc` snapshot or copy a small value inside a short borrow scope.
  Never retain a watch borrow guard across `.await`, expensive work, or publication
  back into that channel.

### Subscribers and service lifecycle

- Replace mesh's callback view with one owned supervisor: process initial state,
  await changes, cancel obsolete initialization/renewal tasks, stop the old client,
  and start the latest desired client. Support None-to-Some and Some-to-None.
- Use `borrow_and_update()` when consuming changes. Watch coalesces intermediate
  values, so supervisors reconcile to the latest desired state instead of treating
  every notification as a command that must execute.
- Replace the same-value mesh mutation used for certificate renewal with an
  explicit restart command to the supervisor. Equality suppression must not lose
  certificate-renewal restarts.
- Replace auth/TLS callback derivation in `run_server_graph.rs` with prepared
  grouped states; retain the startup dependency graph for service initialization.
- Own reload/mesh tasks and shutdown handles explicitly. Dropping a derived view
  will no longer unregister callbacks or cancel services automatically.

### Shared TLS and ACME interfaces

- Add watch-backed certificate/trusted-store and issuer adapters in
  `remote/common/src/security_configuration/`. Update `HasDynamicSecurityConfig`
  and its consumers or add a watch implementation alongside the existing API
  during migration. TLS serving and client-certificate issuance must use the
  same current security state.
- Rewrite `DynamicAcmeConfig` usage in `remote/server/src/server/acme.rs` and
  `acme/certificate_config.rs`. Give certificate acquisition read access plus an
  explicit update sink for generated credentials, cached certificate replacement,
  and invalid-cache removal.
- Tag asynchronous ACME work with its input generation/identity. Reject results
  for a config that has since changed or been disabled; serialize accepted results
  with other config updates before persisting and publishing.
- Once terminal works with watch end to end, migrate other shared
  `DynamicConfig` consumers separately and remove the legacy abstraction only
  when unused. Avoid leaving two writable sources of truth for terminal config.

## Implementation order

1. Introduce ordinary candidate groups, semantic comparison, and explicit reload
   versus startup-only policy. Preserve the file format.
2. Implement stable watch storage and the serialized controller, including
   persistence and changed-only application.
3. Migrate snapshot readers and authentication together, then mesh supervision
   and renewal restart commands.
4. Migrate TLS/issuer adapters and ACME writes; connect them to prepared TLS state.
5. Replace watcher/poll coordination, handle live enable/disable, and implement
   explicit task shutdown.
6. Remove terminal's old wrappers and callback graph. Audit and migrate remaining
   shared users before deleting common infrastructure.

Keep intermediate compatibility adapters narrow and temporary. Their purpose is
to keep each migration step buildable, with the controller retaining sole write
ownership.

## Verification

- Unit tests: stable `Arc<DynConfig>` and channel identities across reloads;
  unchanged values do not notify; changed values reach existing and late
  subscribers; updates persist without receivers; invalid candidates preserve
  active state and can be retried.
- Concurrency tests: duplicate watcher/poll triggers, serialized runtime writes,
  rejected stale ACME results, and rapid mesh changes while initialization runs.
- Behavior tests: password/key consistency, unrelated reloads preserve auth keys,
  terminal/filesystem setting changes, mesh enable/disable, certificate renewal
  restart, watcher/poll enable/disable, ACME persistence, and shutdown cleanup.
- Preserve configuration round-trip coverage and existing password-update browser
  tests; exercise watcher-only, poll-only, and combined reload triggers.
- Run formatting and targeted tests first, then the relevant Cargo server builds,
  workspace tests, and Bazel checks specified in `terminal/AGENTS.md`. Update Bazel
  source/dependency declarations if modules or direct Tokio dependencies change.

## Implementation status

Implemented the terminal migration with one `Arc<DynConfig>` and stable channels
for server/authentication, mesh, ACME, and TLS snapshots. Senders are private;
consumers hold read-only receivers. The server group keeps related authentication
inputs and signing keys together instead of introducing a channel per setting.
A mutex serializes file reloads, password persistence, and generated ACME state.

Removed the terminal root callback graph, dynamic server/mesh wrappers, implicit
save view, and diff wrappers in the candidate/file schema. Mesh has an explicit
supervisor and renewal restart command. Reload coordination supports atomic file
replacement, polling changes, failed-parse retries, and content deduplication.
Unrelated directory events do not reset the polling timer. Startup-only settings
remain fixed in the running snapshot and are retained in the persistence model.

Shared gateway consumers still use a watch-to-`DynamicConfig` compatibility
adapter for their security views. Existing non-terminal callers retain the
legacy ACME constructor; terminal ACME commits use an explicit update sink that
rejects stale results before writing private keys. The shared abstraction remains
until those separate consumers migrate.

Validation: 127 terminal library tests passed (one ignored), 60 common tests and
23 gateway server tests passed. The debug server binary builds with
`no_wasm_build`. Native filesystem event tests require execution outside the
workspace sandbox on macOS. The default nested WASM build could not fetch an
uncached dependency because DNS was unavailable. Bazel execution was blocked by
sandbox cache/socket restrictions; its generated terminal source map was instead
regenerated using the repository's Cargo feature-deps generator and formatted
with buildifier.
